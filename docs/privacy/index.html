This page describes how HealthBot Personal Health Connector is intended to handle information for the owner's own personal, single-user use, what is known now, and what is still unresolved. The connector is intended to run on the owner's own server and to be called over SSH from the shared Grok cloud computer, so Grok Bot / HealthBot can answer the owner's requests.

The project is not an official Oura product. HealthBot Personal Health Connector is not affiliated with or endorsed by Oura Health Oy. This page does not speak for Oura or for Grok Bot. It does not replace the policies of Oura, Grok Bot, or the infrastructure services in the path, and it does not add promises those services have not made.

How to read this page

The owner has adopted this documentation, version 2026-11-08. The connector is not activated. This page describes an intended design and the boundaries known for this version. It does not describe a live collection practice. Where a fact is unverified, this page says so instead of filling the gap.

These website pages are static files. The HTML has no form, no account, and no analytics script. The pages do not ask for health information. They contain no Oura data and no tokens. If a host publishes the files, that host's own logs and retention are separate, and this page does not describe them. Deployment of this version is a separate step.

Whose information

The intended scope is the owner, using the connector for themselves. It is not a service offered to other people. There is no public registration to join. The connector is not a medical device and does not provide a diagnosis, a treatment decision, or emergency care.

Information involved

Authorization and connection material. Access tokens, refresh tokens, and expiry details would be used to open and keep an Oura connection the owner had authorized. OAuth also involves callback information during authorization. A real authorization code or token should not be pasted into a public page or into ordinary chat.

Oura account and health-related data. When a grant and the available records allow it, a read could include identity and email, sleep, activity, readiness, heart rate, workouts, sessions, tags, and blood oxygen. Stress and recovery, cardiovascular information, fitness, and device information could be included only when the API provides them and the grant, device, subscription, and records allow it. This list does not promise that any particular route or record will be available.

Requests and analysis. The owner's requests to Grok Bot / HealthBot, the data the connector returns, and the summaries and analysis can become material the service processes, and they may enter chat.

Operational records. The connector and the systems it depends on can produce status, failure, and operational records. The code design avoids writing successful health-response bodies into error logs. That design does not mean the operating system, the calling platform, chat, or backups are free of the information.

This page is not written on the premise that a real authorization or a live read has already happened. In the work that produced this documentation, no application was registered, no real credentials were supplied, OAuth was not performed, and no live API read was made. An unrelated development application may already exist on the account. These pages do not claim that the account has no application.

Purpose and read limits

The intended purposes are to connect the owner's Oura account, to read data inside a grant the owner would still have to give, to support the owner's own viewing or analysis, and to keep the connection working and diagnose failures.

No live grant has been made. A planning list named eight scopes: email, personal, daily, heartrate, workout, tag, session, and spo2. Calling that list a plan is not the same as holding a grant. A developer interface reportedly lists 11 scopes, including Ring Configuration, Stress, and Heart Health. The scopes that would be requested at activation are unverified. Neither list establishes that every data category is authorized or available. Exact live grants and routes are unverified.

The evidence recorded for this version is that implementation revision fixed65ceeb07 has 35 implemented GET routes, 113 mock tests, and a credential-free handshake covering 36 tools. Those are limited tested metadata. They do not prove a production deployment or a live scope. Whether those 35 routes match every public production route is unverified. They are not all of the data a person can see in the consumer app. The connector is not a way to write health data. Webhook management and sandbox use are outside the health-read description on this page. A connection-status tool is not an extra health-data permission.

Recipients and path

Data read from Oura would first reach the connector on the owner's own server, then pass over SSH to Grok Bot / HealthBot to answer the owner's request. The request and the result may enter chat. When a read happens, the health payload transits over SSH to Grok Bot / HealthBot and may enter chat.

No other deployed recipient is known for this project. That is not a statement that Oura, Grok Bot, or the infrastructure has no service providers of its own, and it is not a promise that information is never disclosed further. This page does not guess which model provider sits underneath, and it does not promise that a platform skips training, keeps nothing, or processes everything on the owner's machine. These pages do not promise zero retention or any limit on training use.

SSH provides a channel. It does not restrict what the far end does with the data, and encryption at rest is not assured. Where processing happens, whether it crosses a border, and how long a particular service keeps a copy are not settled on this page. Those points have to be checked against the services actually used and the policies that apply to them at the time. This page does not adopt a company-only retention arrangement, or a particular close or delete time, as the ordinary retention period for this project.

Storage and protection

Authorization material is meant to persist. Access tokens, refresh tokens, and expiry details are designed to be stored on the owner's server so the connection can continue. They are not memory-only, and this page does not claim that nothing is written to disk. They are not intended to be handed to the shared Grok cloud computer as ordinary call credentials.

Token files are designed to use the platform's data-protection feature. Recovery of that feature depends on a key ring on the same machine. Prior run metadata included a warning that an XML encryptor was not configured. Key-ring contents were not inspected. Only metadata is known. The warning does not prove that a token file is plaintext, and the feature is not an assurance of encryption apart from that server. Encryption at rest is not assured. A person with root access, the same user id, the relevant key ring, or access to a backup may be able to read or recover authorization material.

Token and key directories have been observed with access that is not private to the owning user. Other accounts on the machine may be able to enter those directories. A key file has been observed with access limited to its owner. The home directory has been observed as private to its owner. That file mode does not make the directory private. The operating account can administer the server, and the release location is writable by that account. Those observations are metadata. They are not absolute isolation. The restricted SSH configuration for production calls has not been accepted. Security isolation is being implemented separately. Security isolation is pending and has not been verified. SSH does not provide encryption at rest.

A directory for the connector was created during a credential-free handshake. Its contents were not inspected. The directory does not show that a real token is stored, and its existence is not a claim that the server has no files on disk.

Successful health responses are designed to use a memory cache with a limited lifetime. This page does not state the lifetime, because it has not been verified for this version. A memory cache, and a design that avoids writing response bodies into error logs, do not rule out copies in the operating system, the platform, chat, or backups. They do not mean the whole path never writes health data to disk.

How long information is kept

There is no formal retention setting for the owner, no automatic deletion arrangement that this page can promise, and no promised backup cycle.

  • Authorization material is kept so the connection can continue, and it is stored on the server. After the connection stops, an operator still has to run local logout or another cleanup. Token expiry is not a reason to assume the disk copy or a backup copy disappears.
  • The connector's health-response cache is designed to stay in memory for a limited time. The specific time has not been verified for this version. That cache lifetime does not apply to chat, system records, or backups.
  • Operating-system records, server backups, and Grok Bot chat each have their own retention. No single period is confirmed here.
  • Oura source records, and content held by Grok Bot / HealthBot, follow those services' own functions and policies. Local cleanup by this connector does not delete them.

Local logout, an emptied cache, or a deleted token is not deletion of every related copy.

Stopping, revocation, and deletion

The owner can stop sending requests. An operator can run the connector's local logout. Local logout deletes the connector's local token and clears the connector's cache. It does not revoke authorization at Oura, and it does not delete Oura source records, existing chat, system records, or backups.

Revocation at Oura has to be done in the authorization management Oura provides. Deleting chat or other platform content has to be done with that platform's own functions or by contacting that platform. This page does not promise that those steps instantly clear every backup or every copy. These pages do not name an interface path that has not been verified. Local logout is not remote revocation and is not platform deletion.

Residual files, operational records, or backups on the server have to be cleaned by an operator who has identified where they are and how they are kept. Local logout does not prove that cleanup is finished. This project has no confirmed one-step deletion that reaches every recipient.

Refresh and recovery

If Oura accepts a token refresh and the connector stops before the new token is saved, recovery is not assured and is not exactly-once. A new sign-in may be required. A refresh whose result is unknown is not sent again automatically. An explicit recovery can refresh again and can invalidate the authorization. The operator should confirm the state before doing that.
