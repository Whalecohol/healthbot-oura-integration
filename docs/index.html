HealthBot Personal Health Connector

Not activated. Documentation version 8 November 2026 (2026-11-08). The owner has adopted this documentation. OAuth has not been performed. The connector is not enabled.

Adoption records this description for publication. It does not activate the connector, perform OAuth, or accept another party's terms. The owner's consent does not waive another party's terms. Platform obligations and the technical and legal conditions for use remain unresolved. These pages are not a compliance warranty.

Security isolation is pending and has not been verified. Health data that the connector reads is intended to transit over SSH to Grok Bot / HealthBot and may enter chat. These pages do not promise zero retention or any limit on training use. Encryption at rest is not assured.

HealthBot Personal Health Connector is a personal, single-user connector for the owner. It is intended to take Oura data, within an authorization the owner would still have to give, and to make that data available to Grok Bot / HealthBot when the owner asks to view, summarize, or analyze it.

The project is not an official Oura product. HealthBot Personal Health Connector is not affiliated with or endorsed by Oura Health Oy. These pages do not speak for Oura or for Grok Bot, and they are not an endorsement or an approval. The project does not offer public registration or a hosted connection for other people. This website is static text. It does not run the connector.

What a later read could include

If the owner later activates the connector and completes OAuth, a read could include identity and email, sleep, activity, readiness, heart rate, workouts, sessions, tags, and blood oxygen, when the grant, the device, the subscription, the API, and the account records allow it. Stress and recovery, cardiovascular information, fitness, and device information could be read only when the API provides them under those same conditions. Naming a category does not mean it is granted or that a route will return it.

No live grant has been made. A planning list named eight scopes: email, personal, daily, heartrate, workout, tag, session, and spo2. That list is not a live grant. A developer interface reportedly lists 11 scopes, including Ring Configuration, Stress, and Heart Health. The scopes that would be requested at activation are unverified. Neither list establishes that every data category is authorized or available. Exact live grants and routes are unverified.

The evidence recorded for this version is that implementation revision fixed65ceeb07 has 35 implemented GET routes, 113 mock tests, and a credential-free handshake covering 36 tools. Those are limited tested metadata. They do not prove a production deployment or a live scope. Whether those 35 routes match every public production route is unverified. They are not all of the data a person can see in the consumer app. The connector is not a way to write health data. Webhook management and sandbox use are outside the health-read description on these pages. A connection-status check is not an extra health-data permission.

Results can be missing, delayed, or wrong, and analysis can be wrong. The connector is not a medical device and does not provide a diagnosis, a treatment decision, or emergency care. For illness or an emergency, contact a qualified clinician or local emergency services.

How data would move

The intended path, once the connector is activated, is:

  1. Oura sends authorized data to the connector on the owner's own server. That server is separate from the shared Grok cloud computer.
  2. The shared Grok cloud computer calls the connector through SSH.
  3. Grok Bot / HealthBot uses the result to answer the owner's request. The request, the read result, or the analysis may enter chat.

This is not processing that stays on the owner's machine. When a read happens, the health payload transits over SSH to Grok Bot / HealthBot and may enter chat. SSH is a channel between those machines. It is not a limit on what the receiving service stores or does. Encryption at rest is not assured. These pages do not promise zero retention, and they do not promise that data are kept out of training. Oura's terms and Grok Bot's terms apply on their own. These pages do not replace either set of terms.

Access tokens and refresh tokens are intended to stay on the owner's server so the connection can continue. They are not intended to be passed to the shared Grok cloud computer as ordinary call credentials. That computer is intended to call the connector over restricted SSH standard input and output. The restricted production configuration has not been accepted. Security isolation is being implemented separately. It is pending and has not been verified.

During an authorization attempt, a browser on the Grok cloud computer would use 127.0.0.1:8742, through a temporary SSH local forward, to reach the callback on the owner's server. The recorded note is that a basic test of that forward passed. That result is not a completed OAuth authorization. Real OAuth has not been performed and has not been checked.

The deployment design keeps the connector's service port off the public internet. That design is not a description of the current firewall, and it is not a statement that the server is safe.

Authorization and stopping

Before any activation, the owner would still have to confirm registration materials, the platform terms that apply, the actual OAuth grant, and the production configuration. Reading these pages, or adopting them, is not that confirmation and is not OAuth. In the work that produced this documentation, no application was registered, no real credentials were supplied, OAuth was not performed, and no live API read was made. An unrelated development application may already exist on the account. These pages do not claim that the account has no application.

The owner can stop sending requests. An operator can run the connector's local logout or another local cleanup. Local logout deletes the connector's local token and clears the connector's cache. It does not revoke authorization at Oura, and it does not delete Oura source records, existing chat, system records, or backups. Revocation at Oura has to be done in the authorization management Oura provides. These pages do not name an interface path that has not been verified. Deleting chat or other platform content has to be done with that platform's own functions. Local logout is not remote revocation and is not platform deletion.

There is no confirmed one-step deletion that reaches every place data may remain. Cleanup of residual files, system records, or backups has to be done by an operator who has found where those copies actually are.

Protection, stated at the current boundary

The privacy page states the storage and deletion boundaries in full. In short:

  • Tokens are intended to be stored on the owner's server. They are not memory-only. Encryption at rest is not assured.
  • Root access or the same user id can reach files that account can read. No retention period or backup cycle is promised.
  • Token and key directories have been observed with access that is not private to the owning user. Other accounts on the machine may be able to enter those directories. A key file has been observed with access limited to its owner, and the home directory has been observed as private to its owner. That file mode does not make the directory private.
  • The operating account can administer the server, and the release location is writable by that account. Those observations are metadata. Key-ring contents were not inspected. Security isolation is pending and has not been verified.
